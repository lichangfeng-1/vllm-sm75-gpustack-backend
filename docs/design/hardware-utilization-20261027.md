# 硬件单元利用审计与"不降精度"边界（8×T10，2026-10-27）

口径：本文件回答"int4/int8 算力、张量核心、CUDA 核心、编解码、光栅能不能都用起来"。
所有数字来自 2026-10-26/27 的引擎 trace、隔离微基准与 roofline 计算；不降精度是硬约束。

## 1 各阶段每个单元的占用

| 单元 | 预填（32K） | 解码（8K） | 判读 |
|---|---|---|---|
| **HBM 带宽**（362 GB/s 实测） | 注意力 88%、HC 87–89% | GEMV 合计约 82–100% | 已是主瓶颈 |
| **PCIe Gen3**（13.17 GB/s） | all-reduce 93% | 小消息（5 KB）延迟型 | 已到顶 |
| **FP16 张量核心**（87.2 TFLOPS 峰值，cuBLAS 可达 55.7） | GEMM 时约 64% 可达峰值 | 仅 MoE 用到 | 预填已接近库上限 |
| **INT4 张量核心** | Marlin 专家 GEMM（W4A16） | Marlin 专家 | 已在用 |
| **INT8 张量核心** | 未用（dense 为 fp16） | 未用 | 再量化会降精度，禁用 |
| **CUDA 核心** | elementwise/HC/softmax 等 | GEMV（带宽型） | 已在用；把 GEMM 搬过来只会更慢 |
| **NVDEC / NVJPEG** | 0 | 0 | 纯文本路径不产生媒体负载 |
| **光栅/ROP** | 0 | 0 | 与 token 生成无关 |

## 2 为什么不能把 int4/int8 再往前推

- 专家权重已是 **W4A16（Marlin，int4 张量核心）**；dense 投影是 **fp16**（模型作者的选择）。
  把 dense 降到 int8/int4 会让 logits 变化，违反"不能降低精度"。
- KV 已是 **fp8_e4m3**（早前经 L3 验证可接受）；再降到 int4 会显著掉精度。
- 8-bit 集合通信同理：fp8 量化的逐元素相对误差约 2.3%（CPU 实测），已按新约束作废。
- 结论：**int4/int8 算力能用的地方已经在用**；再用的唯一方式是牺牲精度。

## 3 唯一还没被"用起来"的硬件：编解码

`--limit-mm-per-prompt={"image":4,"video":0}` 说明模型支持图像输入。当前图像解码走
CPU（PIL/torchvision）。若图像请求会成为实际负载，可评估把 JPEG 解码/缩放放到 NVJPEG/NVDEC：
- 收益只在**多模态请求的预处理段**，不影响文本 token 的预填/解码；
- 需要先有图像负载与基线，否则是过度设计。当前不立项。

## 4 不降精度前提下还剩什么

1. **预填 GPU 空闲 ~12.6%**：开场 325 ms 是一次性 JIT；QSA 选页 plan 约 10×17 ms；
   其余 ~650 ms（约 7%）散布在层间。**这是目前最大的一块纯浪费**，需热态 trace 定位（CPU 侧）。
2. **首请求冷启动**：把首次请求触发的 JIT（layer_norm_fwd、_relu_sum_heads、_decode_contiguous、
   _flat_mask）挪到启动 warmup，可省 ~300 ms 首字延迟。
3. **AD 之外的融合**：elementwise/HC 的进一步融合可省几十毫秒，但会改变舍入顺序，需过 L3。
4. 预填/解码的字节数不可再减（精度约束），PCIe/HBM 已满。

## 5 一句话

这台机器上"没用起来的算力"不是 int4/int8 或张量核心（该用的都在用），而是**预填里 7% 的 CPU 空隙**
和一次性的冷启动。继续优化应打这两处，而不是再降精度。
