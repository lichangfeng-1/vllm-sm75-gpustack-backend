# Flash-Next 预填/解码的 roofline 审计（8×T10，2026-10-27）

> **历史快照**：本页是 2026-10-27 Intel AutoRound 档的 trace 与 roofline 推导，**原读数逐字保留**。2026-11-16 对现役 Swift 行 48 的只读审计更正了其中两条**整体推论**（见 §2 末与 §4），并给出两套带宽/算力口径的辨异；现役基线见 [Swift 调优页](../tuning/swift15-prod-20261116.md)。

目的：把每个大项的实测时间与"硬件地板"对齐，回答"还有多少真实余量"。
口径：32K 预填（4×8192 chunk）；带宽取 T10 实测读 362 GB/s；PCIe ring 有效 13.17 GB/s；
cuBLAS fp16 可达 55.7 TFLOPS；fp8 KV 每元素 1 B。
**口径辨异（2026-11-16 现读硬件报告）**：带宽 **read 390 / copy 360–362 GB/s**（本页取的 362 属 copy 口径）；FP16 张量核**峰值 87.21–87.30 TFLOPS**、**cuBLAS 可达 55.68–57.15**（本页 55.7 是当时的代表值）；PCIe Gen3×16 **H2D 12.80–12.81 / D2H 13.18–13.19 GB/s**。**峰值与软件可达分开记，两套口径不可混算。**

| 项 | 实测 | 字节/算力账 | 地板 | 效率 |
|---|---:|---|---:|---:|
| NCCL AllReduce | ~2.4 s（392 次预填） | 每次 42 MB×ring 1.75=73.5 MB；392×73.5 MB=28.8 GB | 2.19 s | **93%** |

## 2 解码（8K 上下文，每步 14.8 ms，trace 口径）

| 项 | ms/步 | 判读 |
|---|---:|---|
| `_row_gemv`（HC 混流） | 3.84 | 单次约 6 MB 权重，82% 带宽 |
| `_gemv_kernel`（gemv_m1） | 2.42 | 白名单三形状 |
| Marlin MoE | 1.52 | 小批延迟型 |
| PCIe-IPC all-reduce | 1.27 | 93 次 5 KB，13.6 µs/次 |
| gemvx | 0.89 | 未进白名单形状（微基准已证无收益） |
| 其余 ~25 项 | ~4.9 | 每项 0.05–0.6 ms |

解码是"约 800 个小内核的延迟链"，GEMV 合计约 7.15 ms 已到 82% 带宽（**单内核口径**）；没有单点 >5% 的空间。

**整步口径更正（2026-11-16 现读）**：整步带宽利用率只有 **47.6%（2512 MB ÷ 13.53 ms ＝ 185.6 GB/s，对 read 390）未饱和**；decode 算术强度 **1.18 FLOP/B**，低于机器平衡点 **223.6**（87.21÷390）达 **189 倍**，算力占用仅 **0.23%** ⇒ 深度访存受限。最大一块不是内核而是**并行布局**：HC（超连接投影）`disable_tp=True`/`ReplicatedLinear` 使八卡各读全份 **1304.8 MB/卡/步＝每步字节 51.9%**，内核本身已达 **84.5% 峰值带宽**。切分可省 **1.0617 GiB/卡**、速度净上界 **15%**，盈亏被新增归约延迟卡住（甲 28.07／乙 36.15／丙 17.40 µs）。**「INT4 硬下限 / 3.6 GiB 每步 / 带宽墙」是循环论证（用 kernel 时间×峰值带宽反推字节），已推翻。**

## 3 还能改什么（按"是否要新东西"）

| 路线 | 上限 | 代价/风险 | 状态 |
|---|---:|---|---|
| 8-bit 集合通信 | 预填 −9~15% | 需自写内核；精度待 q8 探针裁决 | **出局（精度红线，不是等卡）**：用户明令 8-bit 集合通信不得启用；firefly fp8 AR 已入 compat1 仓但默认关、永不默认启用 |
| dense 权重再量化（现为 fp16） | 解码 +10~15%、腾 ~0.8 GB/卡 | 需新权重 + 精度对拍 | **出局（降精度）** |
| MTP | 解码 +20%（**2026-11-16 实测 ×1.27–1.35，均 81.86**） | 262K 撞显存墙：KV 2.25 GiB 时 250K 预填 OOM 差 158 MiB；1.5 GiB 时容量门拒（估最大 195,200）⇒ 实用 ≤ ~195K | **用户裁定不做**（不是「未测封存」） |
| QSA plan 去重/更大切片 | 预填 −1.5~2% | 受 262K 下 8.5 MiB 余量限制（**2026-10-27 spot 口径**；余量真下界须取连续采样极值 502 MiB，算容量用可分配上限 15929 MiB/卡） | 观察 |
| NCCL 参数 | 0 | 实测无差异 | 结案 |
| **HC 八卡复制切分（不降精度）** | **速度净上界 15%、省 1.0617 GiB/卡** | 改上游代码；盈亏被新增归约延迟卡住 | **已立项、计划审查第 1 轮 BLOCKED 后暂停**（最大一块） |
| 启动 I/O（EP 过滤空转修复） | 加载省 ~63 s（**推算**） | 仓内已修、未烘入镜像；须重建切层 | 待用户明示解冻 |

## 4 一句话

这套实现在当前硬件上已接近**该并行布局**的地板：预填 88–93%、解码 GEMV 单内核 82%。要把数字再推一个台阶，
必须减少**传输/读取的字节数**——而减字节**不一定要降精度**：8-bit AR 与 dense 量化都撞精度红线已出局，
**不降精度的那条是 HC 八卡复制切分**（占每步字节 51.9%，净上界 15%，已立项后暂停）。
整步带宽利用率仅 47.6% 未饱和，所以「带宽墙」不是病灶；继续调内核或参数的空间已耗尽。
