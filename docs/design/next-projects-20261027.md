# 下一步两个大方向的设计与 go/no-go 判据（2026-10-27）

> **历史快照**：本页是 2026-10-27 的方向设计。方向 A（SBO）本文已自判「对单请求不成立」；方向 B（解码融合）已于 2026-10-30 实测结案（微基准 −13.3%/层、**端到端 0.00%**，已回退）。2026-11-16 的现役最大一块改为 **HC 八卡复制切分**，见 [Swift 调优页](../tuning/swift15-prod-20261116.md) §6。

前置事实（均有读数）：
- 预填 32K：AR 36%（11.4 GB/s，PCIe 93%）、注意力 88%、HC 87–89%、GEMM 接近 cuBLAS 上限；
- 解码每步 14.8 ms：GEMV 48%（`_row_gemv` 93–95% HBM、gemv_m1 已转正）、Marlin/PCIe-IPC 各约 1.3–1.5 ms；
  **口径声明（2026-11-16）**：14.8 ms 与 2512 MB/步、f=13.53 ms 都是 **Intel AutoRound（Flash-Next）** 的实测账。**现役 Swift 行 48 的 f/m 未单独实测**（`enable_logging_iteration_details=False`），只有面板 decode 66.68 ⇒ T1≈15.0 ms；引用同架构常数时**必须标明是参照不是 Swift 实测**。要定 Swift 的 f/m 须一次重启加开关并按阶梯并发 n=1/4 解方程（生产行禁动，本轮不做）。
- 无精度损失是硬约束 → 量化、fp8 集合通信出局（**精度红线，永不默认启用**）。**MTP 的出局理由已更新（2026-11-16）**：不是「未测」，而是**已实测正收益**（MTP2 decode 85.33/80.35/79.91、均 81.86、×1.27–1.35，接受率 45.1%、τ1.90、FULL 图 3/3）**但撞 262K 显存墙**（KV 2.25 GiB 时 250K 预填 OOM 差 158 MiB；1.5 GiB 时容量门拒，估最大 195,200 ⇒ 实用 ≤~195K），**用户裁定不做**。实测对象为行 26（Intel AutoRound）参数+block400/ConfigB（实验行 53），比值对 Intel 无 MTP 基线 ~63.3（63.30 九档均值）；Swift 权重+MTP2 未实测，同读数对 Swift 66.68 折算约 ×1.19–1.28（均值 ≈1.23），非 Swift 实测收益。
- **不降精度仍能减字节的一条（2026-11-16 现读）**：HC 八卡复制占每步权重字节 **51.9%**，切分可省 **1.0617 GiB/卡**、净上界 **15%**；整步带宽利用率仅 **47.6% 未饱和** ⇒ 旧「带宽墙/INT4 硬下限」定性已推翻。

## 方向 A：SBO（单批计算/通信重叠，借 SGLang #9660 思路）

机制：把一个 prefill batch 切成两半 A/B，两条 CUDA 流；A 做第 L 层的 GEMM/注意力时，B 在同一层或相邻层的
all-reduce 在 NCCL 流上跑，反之亦然。理论上可把 36% 的 AR 藏进计算，预填上限约 **−10%**。

**已做 go/no-go（2026-10-27，8 卡隔离容器）**：
1. 42 MB all-reduce vs 单个约 1 ms GEMM：并发 7.30 ms（和 7.51）→ 只藏住 20%；
2. 但真实比例是"6.4 ms 的 AR 对约 30 ms 的层计算窗"：**32×1 ms GEMM 循环 + 一次 AR 并发 31.93 ms
   （GEMM 单独 30.18、AR 6.38、和 36.57）→ 藏住 73%**。
3. 结论：**硬件层面可重叠（73%）**，但**对单请求不成立**——同一请求的 token 有因果依赖，不能把 batch 切两半并行；
   SBO 只对"多请求混合批"有效。我们的目标是单流 agent，故 SBO **不作为单流主线**，仅在并发>1 的场景保留。
   单流预填目前剩下的可测浪费只有热态 trace 里的 8.7% 空隙（见方向 C）。

## 方向 B：解码的 out_proj + all-reduce + residual 融合（借 vLLM Kimi K3 / Flint 思路）

机制：把行并行 GEMV 的 epilogue 与后续残差相加合并，AR 结果直接写回目标缓冲；目标是把每步 ~800 个内核
压 20–30%。Kimi K3 在 NVLink 上用"直接写 peer 共享缓冲"实现；我们只有 PCIe，需要用 PCIe-IPC 的 push 语义。
可行性未知点：PCIe 写 peer 的延迟（单次 5 KB 消息约 13.6 µs）是否低于独立 AR 内核 + 残差内核的开销。
微基准：2 卡/8 卡上比较 `gemv+AR+add` 三内核 vs `gemv(epilogue 内 push)+add` 两内核。

## 顺序

先做 A 的并发微基准（1 小时内可出结论）；A 不成立再做 B。两者都需独立镜像层与 L2/L3 门禁。

**结案补记**：A（SBO）硬件层面可重叠 73%，但**对单请求不成立**（同一请求 token 有因果依赖），只在并发>1 保留；B（AR⊕RMSNorm 融合）2026-10-30 实测**微基准 −13.3%/层、端到端 0.00%**，已回退 final-v1。**四次「微基准正收益、端到端归零/反转」的前车之鉴** ⇒ 任何局部收益必须过端到端同尺 A/B 才算数。现役最大一块转为 **HC 八卡复制切分**（已立项、计划审查第 1 轮 BLOCKED 12B 后暂停）。
