## 4 显存口径（★算容量一律用 15929 MiB/卡）

```
物理标称            16384 MiB
− 驱动 Reserved       455 MiB   （ECC=Disabled；455 不是 ECC，是驱动 FB reserve，拿不回）
──────────────────────────────
可分配上限          15929 MiB = 15.556 GiB   ← 算容量一律用这个
− CUDA context        303 MiB   （每 rank 一个进程）
──────────────────────────────
引擎初始空闲        15626 MiB = 15.26 GiB    ← 与引擎日志逐字对上
− 权重               9943 MiB = 9.71 GiB
− CUDA graph          215 MiB = 0.21 GiB
──────────────────────────────
可给 KV+激活         5468 MiB = 5.34 GiB
− 现 KV 预算         2304 MiB = 2.25 GiB
──────────────────────────────
未指派给 KV          3164 MiB
```

- **用 16384 会高估 455 MiB/卡、八卡共 3.55 GiB。** 占卡进程只有 8 个 engine rank（各约 14964 MiB），无其它容器偷显存。
- 这也解开了两个历史读数的矛盾：「可见 15929」与「实读 16384」**两个都对、口径不同**（前者＝可分配上限，后者＝物理标称）。
- ★**陷阱：那 3164 MiB 不是可自由分配的额度。** 现读 `Used 15002 + Free 929 ≈ 15929` ⇒ 分配器在负载下已把大部分吃掉。历史连续采样（dmon 归档，各 1304 条）测到 fb 峰值 **15882 MiB ⇒ 真下界 502 MiB**。
- ⇒ KV 实际能安全上调的空间是**几百 MiB 量级（约 +17~40% 容量）**，**不是 3 GiB**；且必须压测 262K 预填峰值＋并发尖峰才能定 util 安全点。
- **余量口径纪律**：凡「余量/容量/峰值/下界」一律取**连续采样极值**并报条数与时间跨度；spot 差值（16384−14998＝1386）只是轨迹上的一个点。PyTorch 缓存分配器随负载单调增长。
- 历史文档里的「每卡只剩 8.5 MiB」是 2026-10-27 Intel 档的 **spot 读数**，与本节口径不同，**不是简单替换关系**。

## 5 四组参数判定（第一性原理：谁执行 → 前置取证 → 数量级先算 → 才谈配置）

### 5.0 一个除法定死所有参数的性质

硬件常数（T10 实测，峰值与软件可达分开记）：FP16 张量核峰值 **87.21–87.30 TFLOPS**、cuBLAS 可达 **55.68–57.15**；带宽 **read 390 / copy 360–362 GB/s**；PCIe Gen3×16 **H2D 12.80–12.81 / D2H 13.18–13.19 GB/s**；**无 NVLink、无 BF16 硬件**。

```
机器平衡点：峰值口径 87.21 ÷ 390 = 223.6 FLOP/B
            可达口径 56    ÷ 390 = 143.6 FLOP/B
decode 算术强度（正向从权重形状×dtype×切分算字节，不用"kernel时间×峰值带宽"反推）：
  每卡每步搬 2512 MB：INT4 仅 153.2 MB、其余 2358.8 MB 是 FP16
  INT4：153.2 MB × 2 元素/B × 2 FLOP = 612.8 MFLOP
  FP16：2358.8 MB ÷ 2 B/元素 × 2 FLOP = 2358.8 MFLOP
  合计 2971.6 MFLOP ÷ 2512 MB = 1.18 FLOP/B
```

**1.18 vs 223.6 ⇒ 低于平衡点 189 倍**；换算算力占用＝八卡 23.77 GFLOP/token ÷ 15.0 ms ＝ **1.585 TFLOPS**，是八卡峰值 697.7 TFLOPS 的 **0.23%**。三个不可回避的结论：

1. decode 是**深度访存受限**，算力几乎全闲 ⇒ 任何「多算一点换速度」的方向（升精度、去 pad、更复杂 kernel）在 decode **收益为零**。
2. 提速只有三条路：**减每 token 搬运字节** / **提带宽利用率** / **投机把一次搬运摊到多 token**。
3. 现带宽利用率 2512 MB ÷ 13.53 ms ＝ **185.6 GB/s ＝ 47.6%，未饱和** ⇒ 第二条路还有空间，**病灶不是「带宽墙」**（旧「INT4 硬下限」定性已作废，那是循环论证）。

### 5.C 声明与生效值不一致（可议，各有明确代价）

**C1 `--gpu-memory-utilization=0.92` 是一条死声明。** 日志原文（`gpu_worker.py:559`）：

> `Initial free memory 15.26 GiB, reserved 2.25 GiB memory for KV Cache as specified by kv_cache_memory_bytes config and skipped memory profiling. This does not respect the gpu_memory_utilization config.`

固定预算 `--kv-cache-memory-bytes=2415919104`（2.25 GiB）完全接管，0.92 一点作用没有。**后果已现读证实**：Swift 权重 9.71 GiB/卡，KV 池却仍是 **339,110 tokens——与 Intel 行 26 逐字相同**，省出的权重显存全变成空闲余量、**没进 KV**。两条路：①**删掉 util**＝零风险、纯免误导；②**改不固定预算**（只给 util、删 `kv-cache-memory-bytes`）＝启动 profile 实际空闲、余量自动变 KV ⇒ 容量↑、利好并发与 MTP 草稿，**但激活峰值安全余量变薄、262K 预填易 OOM**，必须重压 util 安全点（不能拍 0.92 吃满）。

**C2 `--block-size=16` 也不是生效值。** 分配器**覆写成 784**（`interface.py:933`），mamba padding **0.13%**（`:957`）。机制：混合模型强制 **mamba 状态页字节 == attention KV 页字节**；attention 页 ＝ block × 每 token 字节 P，mamba 页 ＝ 固定状态大小 M（与 block 无关）⇒ block 必须 ≈ M/P。align 模式下 `mamba_block_size` 被强制 ＝ `block_size`，**独立的 `--mamba-block-size` 无效**。推论：

```
容量 ≈ KV预算 ÷ 每token字节 P    ← 与 block 基本无关
```

block 只影响 **padding 浪费**与粒度。现态 padding 0.13% ⇒ 浪费已近零，**「block400+mamba16 给 Swift 拿 +1.5% KV」不值得优先排窗口**：那 +1.48%（344,137 对 339,110）是在**有浪费的基线**上拿到的，且这一族**只动容量不动速度**（Intel 上实测 decode 63.25–63.47，与基线同档）。历史对照：block880+mamba fp16 ⇒ padding **120.55%**、KV 338,994 ≈ 基线（省下的全被 padding 吃掉）；block400+mamba fp16 ⇒ padding 0.25%、KV 344,137。

**C3 `--max-num-batched-tokens=8192`，且没有每步上限。** prefill 算术强度 **512 FLOP/B > 平衡点 224** ⇒ 计算受限，大块确实提高 GEMM 效率（实测 prefill 4039/3784/3499 tok/s @8K/16K/32K）。代价可以算出来：

```
一个 chunk 耗时 = 8192 ÷ 4039.33 = 2.03 s
交叉验证：32768 ÷ 3498.81 = 9.368 s，与现读 TTFT 9368.64 ms 吻合
```

本档**没有** `--long-prefill-token-threshold` ⇒ 混合负载下一条长 prompt 的**每个 chunk 会把同批 decode 流卡 2.03 秒**。参照实现用 MMBT 4096 ＋ threshold 2048 把单步 prefill 压到 ≤2048（~0.5 s 卡顿），代价是 TTFT 升高（其 32K TTFT 10.9 s 对本档 9.37 s，+16%）。**判定：单流长上下文没有同批 decode 可卡 ⇒ 8192 合理**；多 agent 并发长上下文时这就是 ITL 尖峰源。属**场景依赖，不是错**；真要改须同包给 TTFT 代价。

**C4 PLE 路径与参照实现不是同一机制。** 容器 `/dev/shm` 64G **只用 1.4M** ⇒ 本档走 `--engram-config={"cpu_offload":true}` 的 **CPU 常驻张量**，**不是**「PLE 表进 shm 跨 rank 共享（`VLLM_PLE_MMAP_MODE=mem`）」那套。0.32 那次 disk→mem 拿到 **+7.8%（47.4→51.2 tok/s）**是**它自己 mmap 实现内部**的对照，按仪器纪律（微基准/局部对照不能外推端到端）**不可外推到本档**；两条路 per-token 成本谁低**无单变量实测**。已知瓶颈定位：PLE 的瓶颈是 **CPU 侧解码**不是 GPU 带宽——历史上按 rank 重排把读量减半只快 **11%**。这是每步时间里最少被优化的一块。

### 5.D 开着但空转 / 预热缺口

**D1 `--enable-ep-weight-filter` 在现役镜像里一个张量都没滤掉。** 四步都取了证：

| 步 | 证据 | 结论 |
|---|---|---|
| ① flag 在不在 | live argv 含 `--enable-ep-weight-filter` | 在 |
| ② 执行者跑没跑 | 日志 `default_loader.py:406`：`EP weight filter: ep_size=8, ep_rank=0, loading 64/512 experts` | **跑了** |
| ③ 判据是什么 | 镜像内 `ep_weight_filter.py:79`：`if not weight_name.endswith((".weight", ".weight_packed")): return False` | 白名单只认两个后缀 |
| ④ 实际张量名 | 现读 `*.index.json`：`…experts.0.down_proj.qweight` / `.qzeros` / `.scales`（expert0 共 **432** 个＝48层×3proj×3） | **没有一个以 `.weight` 结尾** |

⇒ **全部放行、一个没滤**，每个 rank 仍读全部 **512** 个专家的 INT4 权重；**日志那句 `loading 64/512` 是假绿**。调用点已核：`weight_utils.py:962/:979/:997` 三处 `should_skip_weight(name, local_expert_ids)`；`default_loader.py:291` 传参、`:351-412` 初始化（门＝`is_moe and enable_expert_parallel and enable_ep_weight_filter`，`enable_eplb` 时整体跳过）。

**它影响的是加载读量（启动 I/O），不是显存。** **仓内源码已修、镜像未烘入**：本仓 `vllm/model_executor/model_loader/ep_weight_filter.py:84-85` 的白名单已含 `.qweight`/`.qzeros`（提交 `c5b685f`；**`.scales` 保持不滤**——源码注释明写有些后端要全专家的 scale，如 FlashInfer NVFP4 算激活 scale 全局 max）。现役 `…opt15-final-v1` 镜像构建于该修复之前，`compat1` 薄层又从父镜像取原样快照回填、**不夹带** ⇒ **要在生产生效必须重建镜像并切层**，属 GPU 窗口动作，解冻须用户明示。

已验性质（Intel 模型上）：**无损**（64-token 指纹一致）、单 rank 读量 **164.62 → 115.02 GiB（−30.1%）**。**时间收益属推算非实测**：

```
现读加载 209.46 s（rank0 213.94 s）
按读量比例推算 209.46 × (115.02/164.62) = 209.46 × 0.699 ≈ 146.4 s ⇒ 省 ~63 s
```

三重限定：①−30.1% 是 **Intel 模型**上实测，Swift 未测；②按比例折时间是**推算**；③历史那组「127.61 s 对 189.76 s」耗时**含分片组合**，**纯过滤耗时从未单测**。**只动启动 I/O，不动 decode。**

**D2 预热缺口：推理期发生 Triton JIT。** 日志（`jit_monitor.py:141`）：

> `Triton kernel JIT compilation during inference: _ple_conv_kernel. This causes a latency spike; consider extending warmup to cover this shape/config.`（同刻另一条 `_ple_conv_writeback_kernel`）

⇒ warmup 没覆盖 PLE conv 的形状，**产生偶发延迟尖峰**。属每步时间的**偶发项非稳态**，扩预热形状可消，**不改数值、低风险**。

## 7 口径诚实声明（★引用本页数字前必读）

- **2512 MB/步 与 f＝13.53 ms 是 Flash-Next（Intel AutoRound）的实测正向账**，用作同架构参照。
